Security

How Keyvane protects your vault

Plain words first, the specification second. Everything here is implemented identically in the app, the browser extension and the kv command line, and checked against shared test vectors.

Summary

  • Your master password never leaves your devices. Your Secret Key is never sent to us or to your storage; on Apple devices it is also kept in your end-to-end encrypted iCloud Keychain.
  • The vault is encrypted on your device with XChaCha20-Poly1305 before it is saved anywhere.
  • Keys are derived with Argon2id from your password and a 160-bit random Secret Key, so a stolen file cannot be brute-forced.
  • Storage providers and TechHigh only ever receive encrypted bytes.
  • Sharing in organisations uses per-collection keys sealed to each member's public key, with out-of-band key verification.
  • Nobody can recover a vault without the password and the Secret Key. That includes us.

The three secrets

SecretSizeWhere it lives
Master passwordYour choiceOnly in your head (and, optionally, handwritten on your Emergency Kit).
Secret Key20 random bytes (160 bits)Your device's keychain, the printed Emergency Kit and, on Apple devices, your iCloud Keychain (end-to-end encrypted by Apple). Never in the vault file, never sent to us or to your storage.
Vault key32 random bytesInside the vault file, wrapped by the master key. Optionally in the device keychain behind biometrics for quick unlock.

The Secret Key is shown as KV1- followed by 32 Base32 characters in eight groups of four, for example KV1-ABCD-EFGH-IJKL-MNOP-QRST-UVWX-YZ23-4567.

Cryptography

PurposeAlgorithm
Key derivationArgon2id, 32-byte output
EncryptionXChaCha20-Poly1305 (24-byte random nonce, 16-byte tag)
RandomnessOperating-system CSPRNG
2FA codesTOTP, RFC 6238 (HMAC-SHA1/256/512), default 6 digits / 30 s
Key agreement (sharing)X25519 (RFC 7748)
Signatures (sharing)Ed25519 (RFC 8032)
Key derivation from shared secretsHKDF-SHA256 (RFC 5869)

Key derivation

input     = UTF-8(password) || 0x00 || secretKeyBytes
masterKey = Argon2id(input, salt = 16 random bytes, m, t, p, len = 32)

Default parameters are stored in the file so they can be raised later: 64 MiB memory, 3 passes, 1 lane on native platforms; 19 MiB, 2 passes on the web. Because the Secret Key adds 160 bits of entropy, a stolen vault file cannot be brute-forced even if the master password is weak.

Wrapping and payload

vaultKey   = 32 random bytes (created once per vault)
wrappedKey = XChaCha20-Poly1305(vaultKey, key = masterKey, aad = "keyvane:v1:key:<vaultId>")
payload    = XChaCha20-Poly1305(JSON(VaultData), key = vaultKey, aad = "keyvane:v1:data:<vaultId>")

The additional authenticated data binds each box to its vault, so boxes cannot be swapped between vaults. Changing the master password creates a new salt and master key and re-wraps the vault key; items are untouched. Biometric unlock stores the raw vault key in the OS keychain and releases it only after a successful biometric prompt; the master password is still required every 14 days.

Vault file format

A vault is one .kvault file: UTF-8 JSON on the outside, encrypted inside. Without the keys, the only readable fields are the format name, version, vault id, KDF parameters and salt, revision number and save time. Client names, item titles, URLs, field labels and values, notes, tags, attachments and 2FA secrets are all inside the encrypted payload.

{
  "format": "keyvane.vault", "v": 1, "id": "<uuid>",
  "kdf":  { "alg": "argon2id", "m": 65536, "t": 3, "p": 1, "salt": "<base64>" },
  "key":  { "n": "<base64 nonce>", "c": "<base64 ciphertext+tag>" },
  "data": { "n": "<base64 nonce>", "c": "<base64 ciphertext+tag>" },
  "rev": 12, "saved": 1730000000000
}

Sync merges by record: a record on one side only is kept; the newer version of the same record wins and the older one goes into that item's history, so nothing is lost. Uploads use the provider's revision tag, so a newer remote file is merged, never overwritten.

Sharing and organisations

A Keyvane Cloud account (or an account on your own server) has two key pairs generated on your device: X25519 for receiving keys and Ed25519 for signing. To sign in, the client sends only an authentication key derived from your master key with HKDF; the server stores an Argon2id hash of it and never sees the password.

  • Each shared collection is encrypted with its own random key and a key version.
  • A key grant seals a collection key to one member's public key (X25519 sealed box, HKDF-SHA256, XChaCha20-Poly1305) and is signed by the person who shared it. Unsigned or wrongly signed grants are refused.
  • Before anyone receives keys, their five verification words (derived from their public keys) are compared by voice or in person, then certified by the approving admin. Clients trust a key only through such a certificate chain back to the organisation creator.
  • Offboarding rotates the key of every collection the person could open and re-encrypts the data; old keys cannot read anything saved afterwards.
  • The activity log is signed by the author and sealed to an organisation audit key that only owners and admins hold.

Threat model

What Keyvane protects against

  • A stolen or leaked vault file — from a cloud breach, a lost laptop backup or a shared drive. Without the password and Secret Key the file is unreadable, and the Secret Key makes guessing infeasible.
  • A curious or compromised storage provider, including Keyvane Cloud. Providers see encrypted bytes, file sizes and timestamps, nothing more.
  • A malicious Keyvane Cloud server. Public keys are verified out of band and certified; every key grant and audit key is signed; ciphertexts are bound to their ids, organisation and key version, so they cannot be swapped around. The server cannot read or forge encrypted data, and cannot trick clients into encrypting to a key it knows.
  • Tampering with files — authenticated encryption detects any change.
  • Someone who used to have access — key rotation on offboarding stops them reading anything new.

Honest limits

Encryption protects people who have no key. It cannot protect you from things that happen on an unlocked device, or from people you chose to trust. Specifically:

  • Autofill-only is enforced by the app. Someone with the collection key and a modified client could still read it. Choose people accordingly. Crypto guarantees apply to people who have no key.
  • Roles and access lists are enforced by the server. A malicious server could hide data or deny service, and could show you a stale view, but cannot read or forge encrypted data.
  • The organisation creator's key is trusted on first use. Compare the owner's verification code once if you want to rule out a server lying on day one.
  • Five words are about 64 bits — fine for a live comparison, not a long-term identity.
  • The activity log records what Keyvane apps report. It cannot see copies made with other tools after someone legitimately viewed a password.
  • Policy checks for password strength are guidance. The server cannot see passwords.
  • Rotation cannot un-see data. After offboarding, Keyvane lists the passwords the person could see so you can change them at each service.
  • Malware on an unlocked device can read what you can read. Keyvane limits the window with auto-lock, clipboard clearing and screenshot blocking, but no password manager can defend an owned device.
  • Lose both your password and your Emergency Kit and nobody can recover your vault. This is a deliberate property, not a missing feature.

On your device

  • Biometric quick unlock, with a master password re-check every 14 days.
  • Auto-lock after inactivity; clipboard cleared automatically after copying.
  • Screenshot blocking on platforms that support it.
  • Atomic saves with a local backup copy, so an interrupted write cannot corrupt the vault.
  • Key derivation runs in the background so a slow Argon2id never blocks the UI into weaker parameters.
  • Emergency Kit PDF generated at sign-up for printing.
  • The web app runs under a strict Content Security Policy and uses lighter Argon2id parameters; it is intended for emergency access rather than daily use.

Responsible disclosure

If you believe you have found a security problem in Keyvane, the Keyvane Cloud server, the browser extension, the CLI or this website, please tell us privately first.

  • Email security@techhigh.co.uk. Include steps to reproduce, affected versions and, if you have one, a proof of concept.
  • Machine-readable contact details are published at /.well-known/security.txt (RFC 9116).
  • We aim to acknowledge reports within 3 working days and to keep you informed as we fix the issue.
  • Please give us reasonable time to fix before publishing, do not access or modify data that is not yours, and do not run tests against Keyvane Cloud that could degrade service for others.
  • We will not take legal action against researchers who act in good faith and follow these guidelines, and we are happy to credit you when the fix ships if you wish.

An external security audit of the core library, the server and the extension is planned before public launch. This page will link to the report.
